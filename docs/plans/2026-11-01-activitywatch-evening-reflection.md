# ActivityWatch 辅助的晚报前回顾

日期：2026-11-01。状态：第一阶段已实现（分支 `claude/ai-phase2-de8bd4`），实现说明见第 9 节；第二阶段（自动推荐片段）未做。

## 1. 产品判断（讨论后的修订）

目的：帮助用户发现不满意的时间安排，理解原因，并尝试一个具体调整。现有任务完成记录继续承担成果记录；ActivityWatch 提供额外的时间线索。

推荐形态：一条中性的全天时间线 + 默认一张回顾卡 + 一项可采纳的调整。全天记录可展开，但不要求全天逐段认领。任务关联是按需补充，不做自动匹配，不作为生成晚报的门槛。

这次修订替代原来的“5–8 个片段、逐段推荐任务、确认进展”流程。也不采用讨论中“把全天固定分为 3–5 块并全部点选”的要求：大块仍可能混合多个任务、休息和缺失记录，按钮少不能证明负担小。

需要纠正的假设：

- IDE 停留时长不能证明有效工作，视频不能证明摸鱼，窗口切换不能证明打断，AFK 不能证明休息。
- 软件类别无法可靠给出“精力分布”“生产力分数”或“拖延时长”。禁止用红黄绿把用户分为产出、沟通、游离。
- 未完成任务不等于没推进；完成任务也可能值得复盘投入与优先级，但这些含义需要用户确认。
- “零羞耻感”“30 秒完成”“100% 准确”“测谎仪”不是已有证据，不写进产品承诺。这里讨论交互假设，不据此做心理诊断。
- 不追求“用户无法糊弄”，而是提供能纠正记忆、又允许质疑记录的入口。若要求每段都给解释才能继续，就会奖励敷衍标签。

本方案针对用户明确提出的个人工作流；没有核查上游社区的广泛需求。是否长期接入 AW，应以它能否带来仅看任务列表得不到的有效回顾为判断依据。

### 当前晚报的缺口

`AiReportDataService.collectEvening()` 当前通过 `_aggregate([today])` 返回 `trackedToday`（包括计时和 `doneTasks`），并收集未完成任务和逾期任务。`_aggregate()` 合并当前任务与 young archive；`aggregateWeek()` 按 `isDone && doneOn` 筛选完成日期，并限制完成项为 40 条。完成日期当前用 `getDbDateStr(new Date(doneOn))`，实施时须核对它与应用逻辑日边界的一致性，不能把当前数据当成完整的历史事件账本。`AiReportService._collectInput()` 再加入早报和周方向。当前没有 ActivityWatch 活动解释字段。

`AI_EVENING_REVIEW_PROMPT` 要求解释未完成工作“why it probably slipped”，列举估时、打断、过度计划。这是模型猜测原因的入口；新的流程应把原因的权威来源改成用户确认，未知则明确未知。

`AiSchedulerService.tick()` 到时直接调用生成。仅在手动按钮前加一个弹窗，会导致自动晚报绕过回顾。两条入口必须共享同一前置流程。

当前 Daily Summary 已有任务、计时、日终记录和评价入口。应当在它的基础上补充回顾，并从已有晚报按钮打开同一位置，无需新增一级“AI 活动分析”页面。

以下均为 2026-11 查阅的厂商公开文档，未进行产品实机体验。比较范围仅限活动回顾、确认与任务归属。

| ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ---------------------------------- | -------------------------------------------------------------- |
| [Timely Memory](https://www.timely.com/help/handbook/autosheet/memory-101/) 与 [经典版说明](https://www.timely.com/help/handbook/classic/memory-101/) | 从原始 memories 聚合活动，在时间线上回看 | 用户可将时间分配到项目和任务并调整 | 借鉴“先聚合、再确认”；不引入计费和团队工时流程                 |
| [Rize 官方文档](https://docs.rize.io/)                                                                                                                | 后台采集后通过 inbox 与 timeline 回顾    | 纠正错配、标签与关键词             | 借鉴优先处理需要注意的条目；不为每个片段增加标签维护工作       |

采纳：时间线辅助回忆、先聚合、用户可纠正解释、私密活动可排除、从回顾走向一次小调整。

刻意不做：逐分钟报账、团队监督、排行榜、把某类网站固定判定为低价值、自动把活动时长灌进正式工时。

## 4. 最小用户流程

### 4.1 进入每日总结，已有成果直接显示

沿用现有已完成任务、任务计时和未完成任务，不再要求重新确认全部任务。补充未完成进展、计划外事项的入口保持可选。

“已完成”表示任务系统中的状态，不等于任务之外的所有工作；列表受来源与截断限制时要明确说明。

### 4.2 展示一条中性时间线

默认显示一条紧凑的全天时间线，并按上午、下午、晚间展示少量应用/标题线索，避免把记录完全藏进可选入口后又退回凭印象反思。详细事件和标题通过“展开活动”查看。分组只是导航，不代表连续工作或单一任务；不要求每组回答问题。当前逻辑日仍由应用日期设置决定，不因这些标题改变边界。

每段展示：时间范围、应用/标题线索、已观察活动时长、闲置记录和无窗口记录区间。无窗口记录的原因可能是采集未运行、窗口不可见或其他情况，未知时不定性。详细标题留在本地展开。

原始事件先按时间裁剪和去重；可把相邻相同应用事件合并展示，但保留标题和子区间以便展开。展示层可以压缩碎片，统计层不能把首尾跨度全算成工作时长。

不要求给所有记录分类，不显示“尚有 42% 时间未解释”等完成率。没有线索的区间不能为了“全天覆盖”补造记录。

### 4.3 默认只打开一个回顾问题

首版由用户选择焦点：

> 今天有没有一段时间，你希望重新安排？
>
> [选一段看看] [整体还可以] [今天先结束]

选中片段后，先问“你怎么看这段安排？”，而不是预设“是什么卡住了你”。同一套选项适用于所有软件，不按软件类型预先分成产出卡和摸鱼卡：

- 符合当时的安排（包括工作、学习和主动休息）
- 做着做着超出了原本打算的时间
- 一直没开始本来想做的事
- 遇到阻碍，没推进下去
- 临时换了优先级
- 记录不代表当时的情况 / 记不清

另有自由输入，可多选，默认不选中任何原因。选择“符合安排”后就结束该片段；选择“记录不代表情况”时允许说明线下活动、学习阅读等，不能要求用户先自证。

仅当用户选择想调整的情况，再给一次可选追问：“当时最主要的影响是什么？”可选下一步不清楚、复杂度超出预期、外部插入、疲惫、没察觉已经超时、其他/不确定。用户选择只代表自述，不能据此宣称唯一根因。

可选“关联任务”：手动搜索已完成或未完成任务、子任务与归档任务；一个片段可提及多个任务，但不分配工时。关联只是“这次回顾涉及这些任务”，不是“整段都花在这些任务上”。

默认一次回顾一段；用户主动点“再看一段”才增加，不用自动补题凑到两道。用户选择“今天先结束”后不再偷偷分析“从几点脱轨”，也不自动在明天补发今天的问题。

### 4.4 用真实记录产生提醒，而不替用户下判断

自动挑片段放到第二阶段。首版先验证时间线是否帮用户发现新的问题，以免同时引入候选算法和交互负担，无法知道哪里有效。

第二阶段最多主动推荐一段，提供“为什么推荐”和“换一段”。候选可以来自前台应用切换较多、某个应用停留较长或用户之前主动选过的观察主题。描述仅限记录，不命名为逃避、深度工作或时间黑洞。

切换统计用相邻的前台应用变化，不直接把窗口标题变化次数当作任务切换。阈值先通过本机记录展示和用户纠正调整，不宣称统一的“每分钟几次就是低效”。无可信覆盖或缺少候选时不提问，不把数据缺失排成最严重的问题。

早报是建议，不能默认已被用户采纳；当前早报也没有精确时段承诺。禁止说“14–16 点原计划做 A”，除非存在用户确认的对应计划。

## 5. 示例：反思到可尝试的改变

以下为说明性示例，不是用户当天数据：

> 13:30–15:10 的记录包含浏览器、编辑器和聊天应用。
> [展开标题与时间分布]
>
> 你怎么看这段安排？
> 用户：做着做着超出了原本打算的时间。
>
> 当时最主要的影响是什么？（可跳过）
> 用户：没察觉已经超时。原本只想查一个样式问题。
>
> 涉及哪个任务？（可跳过）
> 用户：已完成的“调整首页样式”。

可生成的晚报：

“你提到样式调整超出了自己的预期，主要是不容易察觉时间已经过去。明天可以在开始这类小修补时先约定一个停止检查点，届时决定继续、缩小范围还是留待以后。”

不能生成：“你在低价值任务浪费了 100 分钟，导致重要任务失败。”关联不证明全部时长，任务价值与后续因果也未确认。

由用户选择是否采纳一个调整。首版把调整记在报告中，次日仅邀请反馈“有帮助 / 没用 / 没试 / 不适用”，不自动创建提醒或任务。需要调日期等实际任务修改时，沿用既有确认入口；当前晚报建议工具不支持自动拆子任务，不能用提示词伪装成已实现能力。

## 6. 数据与生成契约

报告输入分开携带以下信息，避免后续模型把推测写成事实：

| 输入                  | 来源与含义                                                         |
| --------------------- | ------------------------------------------------------------------ |
| taskFacts             | 当前任务状态、实际记录的计时；注明范围和截断                       |
| activityObservations  | 设备、起止、应用使用统计、覆盖限制；不能携带自动生产力结论         |
| userReflection        | 用户选中的片段、所选描述、补充文字、可选任务引用；均为用户自述     |
| reviewDisposition     | 已回顾、认为安排可以接受、主动跳过或尚未回应；这些状态不能混用     |
| priorChosenAdjustment | 上次用户已采纳的尝试及其反馈，可为空；本次尚未生成的建议不属于输入 |

保留源事件 ID（可用时）、bucket、片段起止、来源版本/取得时间和用户确认时的摘要。只保留必要的已选择摘要，不复制整天原始记录。重新获取数据不得覆盖用户回答；来源变化时让用户选择是否重看，生成使用明确的输入快照。

晚报输出包括已有成果、用户确认的一个发现、一个可采纳调整。没有发现时可以只总结现有事实；不把“未回顾”解释成逃避，不通过软件类别推断懒惰、精力或工作质量。

选择了未完成任务且描述“有推进”，报告可以表达推进，但不写完成。选择了已完成任务，也不能反向推断它占用了选中片段的全部时间。所有回顾编辑都不直接改任务状态或计时。

当前 `AiReport` 保存日期、正文、建议等，没有结构化的早报计划快照或用户采纳计划记录。第一版不做“计划承诺违约”判断；如果以后要计算计划偏差，应保存用户采纳的任务集合及版本，不能把模型早报正文当成承诺。

日期采用应用逻辑日及用户时区，查询使用明确时区边界；窗口、网页与 AFK 用区间运算，不相加。AW 与 `timeSpentOnDay` 口径并列展示，不算“遗漏工时”，不自动补录。区间跨日须裁剪。

### 生命周期

草稿按逻辑日和设备保存，包含状态、修订号、用户选择与报告引用。状态为待回顾、编辑中、可生成、生成中、已生成、失败；“已回顾/接受安排/跳过”作为独立决定保存。

当前 scheduler 到点直接调用 `generate()`；改造后将“草稿已准备”和“报告已生成”分开。启用回顾时，生成按钮要求用户明确选择提交回顾、接受当前安排或跳过本次回顾；无任何操作不调用模型。同一天重复 tick 不重复提示。未回应保持待回顾；用户手动结束时可生成仅基于任务记录的晚报，不因缺少 AW 或漏答而阻塞。

生成身份使用日期、设备和输入快照修订号；同版本重复点击复用已保存结果。用户回答、选中观察、提交排除项或用于报告的任务状态/计时改变时，下一次主动生成创建新快照并递增修订号；旧快照保持不变。后台刷新不自动重新生成，也不覆盖已经确认的回答。失败保留回答后重试，重启后核对是否已有报告，避免重复落库；不能承诺网络不确定时远端模型调用绝对一次。修改回答后可主动重新生成并标识替代关系，旧报告已采纳建议不得因重生成再执行。

生成后在报告卡提供“试试这个调整”，点击后以报告 ID 与建议 ID 保存采纳记录（文本、采纳日、目标逻辑日、反馈状态）。采纳不要求重新生成报告。次日打开每日总结时显示一条可关闭的跟进入口；一旦回答或关闭便记录状态，不再次显示。未打开页面不主动弹窗，不把未尝试视为失败。旧草稿可主动返回查看，但不累计红点和待解释欠账。

### 隐私与保留

原始标题和 URL 只在本机展示；用户确认后，向已配置模型提交选中片段的最小摘要和解释。生成前可查看提交内容、排除敏感内容。远端 AI 调用仍可能让摘要离开设备，不能把本地存储表述成全链路不出设备。

原型草稿沿用 AI 数据库的本地范围，不加入同步或现有备份；界面明确这一点。提供删除当天回顾及相关摘要的入口。建议已生成回顾保留最近 30 个逻辑日供短期对照，旧未回应草稿在逻辑日切换后移出待办入口；具体自动删除期限应在启用时明确，已保存晚报沿用其自身保留规则，不因清理草稿悄悄删除。

## 8. 交付顺序与验收

### 第一阶段：能用的最小闭环

同一次交付打通当前设备 AW 读取 → 中性时间线 → 用户选一段 → 可选原因和任务引用 → 晚报 → 草稿恢复。保留无 AW 手动回顾退路。先不开发自动诊断、自动任务匹配、红黄绿评分或全日归因表。

实现前核对日终页面、AI 本地存储、Electron 桥接的现有约定。只读查询实际 AW 进行连通性验证；不需要改动原始记录。

### 第二阶段：确认值得继续后再推荐片段

只有时间线确实帮助用户找回了原本没意识到的安排问题，才加入本地候选排序与“帮我挑一段”。当多数推荐都只是正常查资料或跨软件工作时，应取消该推荐规则，不通过更强的提问弥补识别不准。

个人试用可先观察约一周，作为产品反馈，不作心理学实验或因果效果证明。只问三个问题：是否因记录想起了新问题、是否愿意继续用、上次的小调整是否值得保留。反馈不接遥测，不以标签数量和解释覆盖率评价用户。

### 验收场景

1. 同一 IDE 中处理多个任务：不自动归属任务，不把整段计给某一个任务。
2. 用视频学习、长时间阅读被判 AFK：显示原始观察，用户可以认可该安排，报告不判拖延。
3. IDE、终端与浏览器频繁切换正常排障：不称为低效；用户确认顺畅后不追问。
4. 已完成任务投入超预期：允许选中反思；不自动推断其价值低或它导致其他任务失败。
5. 未完成但有推进：保留用户描述，不改完成状态；线下工作可直接补充。
6. 一段混合多个任务和休息：可缩小选区或只描述问题，不强迫精确分账。
7. AW 无数据、缺少 AFK、跨日、重复/重叠窗口与网页：明确覆盖边界，时间不重复相加。
8. 未回应时保持待回顾且不自动生成；接受安排或明确跳过后可生成，但二者含义不同，均无拖延推断；低状态出口不再分析“脱轨时间”。
9. 定时与手动同时触发、重启、失败重试、重新生成：共用草稿，不重复落库、不重复执行建议。
10. 早报未采纳或没有早报：不拿模型建议当用户承诺，不杜撰精确计划时段。
11. 隐藏敏感片段：请求中没有原始标题或 URL；可核对实际发送的最小摘要。

实现验证包括区间函数与状态服务的单元测试、真实 AW 连通性、完整页面流程和报告输入输出抽查。修改 TS/SCSS 后必须跑 `npm run checkFile`，并执行对应 Angular/Electron 检查。本次仅修订产品方案，未实现这些功能或声称验收通过。
